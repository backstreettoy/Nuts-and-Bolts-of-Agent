# 第六章——Skill按需加载的知识

Skill 是磁盘上的一个文件夹，只有当智能体判断它与眼前的任务相关时才会去读。这一句话已经把整套设计讲完了：打包的单位是文件夹而不是函数，装的是说明文字而不是编译后的代码，触发的方式是判断而不是查表。计算机曾用动态库解决过同样的问题：系统一次能容纳的流程有限，怎样才能让更多流程随时可用？Skill 给出了另一种答案，值得探究的正是这三处差异。本章先讲 Skill 是什么、一次调用如何完成，再讨论实际使用中容易让人意外的细节。

在计算机里，程序需要调用自身没有的例程时，会按名称查找。加载器在磁盘上找到库，把它映射进地址空间，把名字绑定到地址，例程就跑起来了。这里有三个特点：解析依靠精确的名称，要么绑定成功，要么在加载时报出明确的错误；载入的代码供处理器执行，不需要像文字一样阅读，因此占用的是地址空间，不是处理器的注意力；库只通过入口点与调用方交互，对调用方的影响也限于调用点允许的范围。

到了智能体这里，这三个特点都变了。解析依靠语义：模型读一遍已安装 Skill 各自的一行描述，挑出与任务相符的那个。挑漏了，智能体就退回通用知识，照样给出通顺的回答，于是失败表现为略有偏差的输出，而不是一条报错。载入的材料是模型要读的文字，每一行都占用上下文窗口，而上下文窗口是整个系统里最稀缺的资源。这些文字还与其他所有指令一同进入上下文，因此 Skill 也会影响模型如何理解任务的其余部分。从名字到语义，从执行到阅读，从隔离的代码到共享的话语权，本章接下来就围绕这三处变化展开。

## 6.1 概念、目标与结构

### 6.1.1 什么是 Skill

Skill 是一段可复用的流程，智能体只在任务需要时才把它加载进来。它把做一件事的办法整个打包——步骤、约定，以及可能附带的代码——好让智能体照着一套现成的方法走，而不必每次从头推演。填写 PDF 表单、按公司规范排版报告、把仓库的提交记录整理成发布说明，这些流程都值得写下来，供以后随时取用。这样做有两点好处：Skill 按需加载，使用前几乎不产生开销；又能以文件夹的形式长期保存，不受一次对话的限制，可以像其他文件一样复用、做版本管理、走评审。在聊天框里输入的一段提示词不具备这两点好处，只能在当次对话中发挥作用。

最小的 Skill 是一个目录加一个文件 `SKILL.md`。这个文件分两部分：YAML frontmatter 里放 `name` 和 `description`，Markdown 正文里放说明。其余内容都可按需添加，放在同一个目录下：

    pdf-processing/
    ├── SKILL.md          # 必需：frontmatter + 说明
    ├── FORMS.md          # 更深一层的流程，需要时才读
    ├── REFERENCE.md      # 查阅用：schema、字段表、示例
    ├── scripts/
    │   └── fill_form.py  # 代码，拿去运行而不是拿去读
    └── assets/
        └── invoice.docx  # 模板、图标、样例数据

文件夹里装着三类内容，选择哪一类，考虑的都是同一个问题：这一步该给模型多少自由度？自由度最高和最低的两种做法都不陌生。普通程序是完全确定的，它处理作者写下来的那些情况，每次运行的处理方式都一样。纯说明文字则相反，能覆盖作者没有列举过的情况，代价是各次运行的结果会有出入。自由度换来更广的覆盖面，确定性让结果可以重复；编写 Skill，就是为每一步选择合适的自由度。三类内容对应三种自由度：**说明文字**提供灵活的指引，模型可以按实际情况调整，自由度最高；**代码**规定固定的行为，适合用于结果必须准确、唯一的步骤，自由度最低；**资源文件**介于两者之间，事实本身固定，模型可以灵活决定如何使用。写得好的 Skill 会为各部分选择合适的形式：需要判断的用文字说明，算术和文件操作交给脚本，原本需要模型凭记忆回答的内容写进参考文件。

Skill 也是智能体里最容易改动的那一块。加一个是复制一个文件夹，改一个是编辑 Markdown，删一个是删掉文件夹。这样，一个团队可以备有几百个 Skill，常驻规则的清单仍然很短。

### 6.1.2 智能体如何找到、加载并运行 Skill

每次使用 Skill 都要经过三个阶段：智能体找到 Skill，加载说明，再按说明执行任务。完成这三步，只需使用智能体已有的工具，不需要加载器、链接器或其他机制。下面以 `pdf-processing` 为例，按顺序看一遍各阶段用了什么工具。假设用户要提取一份扫描版报告里的表格。

1.  **对话开始之前，Skill 还未加载。** 运行时扫描各个 Skill 文件夹，把每个 `name` 和 `description`，连同文件夹路径，抄进系统提示词。Skill 的其他内容一概不加载。此时模型对 `pdf-processing` 的了解仅限于这一小段信息，无论最终是否用到这个 Skill，这段信息都会留在上下文里。

2.  **请求到达，智能体找到 Skill。** 模型在同一份上下文里读到请求和 Skill 描述，将“扫描版报告里的表格”与 `pdf-processing` 匹配起来，再通过唯一可用的方式采取行动：发出一次工具调用。这次调用交给文件读取工具，内容是“读 `<folder>/SKILL.md`”。模型本轮的工作到此结束，接下来等待文件返回。

3.  **文件回来，Skill 完成加载。** 运行时在模型外部执行这次读取，也就是第 3 章讲过的那套陷入与返回，再把文件内容作为工具返回结果追加进对话。`SKILL.md` 的正文就这样进入上下文窗口，供模型下一轮读取。加载的过程就是由工具将文件内容放进对话。

4.  **模型读到说明。** 其中有一行写着，扫描件由 `python scripts/extract_tables.py <input>` 处理。这一行与正文里的其他内容一样，只是一句说明，模型此时也只是读到了这句话。

5.  **模型运行脚本，这是第二个工具，也是第二道边界。** 模型再发出一次工具调用，这次交给 shell 工具，命令字符串由它自己拼出来：`python /home/user/.skills/pdf-processing/scripts/extract_tables.py report.pdf`。把第 4 步那行文字变成动作的，正是 shell。没有它，那一行就只是一行字。

6.  **shell 返回输出。** 命令在模型外部运行，脚本打印的内容作为一条新的工具返回结果进入对话。模型读到这份输出，也就是抽取出来的表格，接着往下做任务。

第 5 步还有一个细节值得说明：命令里的那条长路径是怎么来的？正文里写的是相对路径 `scripts/extract_tables.py`，命令里带的却是绝对路径 `/home/user/.skills/pdf-processing/scripts/extract_tables.py`。模型以第 1 步提供的 Skill 所在目录为基准，拼接相对路径，得到绝对路径，而不是以当前工作目录为基准。这次拼接，正是元数据一开始就要带上文件夹路径的原因。路径也只有在这次拼接时可能出错：最初这条命令由模型直接拼成字符串，没有检查器验证。脚本一旦启动，内部的 import 和文件路径就由普通软件的解析机制处理，出错时会明确报错。稳妥的做法是让脚本根据自身位置查找同目录下的文件，这样只有最初拼接命令时需要模型判断根目录。

第 5 步里的 `python` 也值得一提：它同样不是工具，而是环境中的解释器，Skill 通过 shell 调用它。6.1.4 节会划清工具与其背后环境的界线。

第 5 步还有一个关键问题：模型凭什么知道这个名字对应一个可以运行的程序？这个程序并没有经过注册。工具清单里只有一个通用的 shell 工具，而这个工具接受的是一个字符串。脚本名只是 Markdown 文件里的普通文字，模型读到后将它写进工具参数。这里没有可执行文件表，也没有入口点；在 shell 实际运行命令之前，没有任何机制确认过文件是否存在。程序中靠“登记”完成的事，在这里要靠三方面配合：正文要求运行脚本，说明了调用意图；通用 shell 工具允许执行任意程序；剩下的交给解释器，`python foo.py` 要么成功运行，要么报错退出，两种结果都以文字返回。

第 1 步提到的元数据清单如下。运行时在启动时读取每个 Skill 的 frontmatter，加上文件夹路径，拼成这段文字：

    The following skills are available. When one fits the request,
    read its SKILL.md at the given path before continuing.

    <available_skills>
      <skill>
        <name>pdf-processing</name>
        <description>Extract text and tables from PDF files, fill forms,
        and merge documents. Use when the user mentions a .pdf file or asks
        to pull data out of one.</description>
        <location>/home/user/.skills/pdf-processing/SKILL.md</location>
      </skill>
      <skill>
        <name>release-notes</name>
        <description>Turn a repository's commits since the last tag into
        release notes in the team's format. Use when the user asks for release
        notes, a changelog, or "what shipped".</description>
        <location>/home/user/.skills/release-notes/SKILL.md</location>
      </skill>
      <skill>
        <name>expense-report</name>
        <description>File an expense report from receipts. Use when the user
        mentions expenses, receipts, or reimbursement.</description>
        <location>/home/user/.skills/expense-report/SKILL.md</location>
      </skill>
    </available_skills>

三个 Skill，三条记录，没有任何一行来自正文。不同运行时的标记形式不一样，有的用标签，有的用普通的 Markdown 列表，但三个字段是固定的：一个名字、一段从 frontmatter 原样抄来的描述、一条待读取的路径。每条记录大约一百个 token，这就是安装一个 Skill 后的全部常驻开销。这份清单还说明了两件事。这些描述并排放在一起，模型通过比较来选择，而不是逐个独立判断；描述一旦重叠，就会相互干扰，6.2.4 节会讨论这个问题。此外，描述会原样提供给模型。模型选择 Skill 时，作者能用来影响选择的，只有 frontmatter 里的那两句话。

再回到第 1 步，元数据块也有同样的问题：模型为什么会把这些文字当作 Skill 清单？那段内容一样是纯文字，里面没有任何标记说明某一行是一个 Skill 而不是一条笔记。模型之所以照着清单行动，也依靠三个条件：运行时在清单前加上引导语；记录中的路径指明要读取的文件；模型在训练中见过这种模式，即便引导语很简略，也会遵循这个约定。最后一点在计算机里没有对应的机制：这套机制有相当一部分来自模型权重，而不是提示词。验证起来很容易：把一段等价的内容贴进普通的用户消息，模型的表现大致相同。没有发生任何登记，Skill 照样能用。这也正是 Skill 需要评审的原因：任何能把文字放进窗口的东西，都能宣布一个 Skill 的存在。

第 4 步提到的脚本体现了一条通则：正文通过在说明中写出文件名，引用同目录下的文件。这里没有 import 语句，也没有链接器。正文写出相对路径，模型读到后判断相关说明是否适用，再发起读取或运行操作。

    填写表单前，先读 `FORMS.md`。
    字段名对照表在 `REFERENCE.md`。
    校验填好的文件，运行 `python scripts/validate.py <input.pdf>`。

据此，编写正文时要注意三点。

1.  **引用文件时要说明使用条件。** 模型根据文件名周围的说明判断是否打开文件，因此_什么时候用_和_文件里是什么_同等重要。光给一串文件名，模型没有任何判断依据；写成“PDF 带可填字段时读 `FORMS.md`”，依据就齐了。

2.  **读取文件和运行脚本占用的上下文不同。** 正文指向的 Markdown 文件按全文长度进入窗口；正文指向的脚本留在窗口之外，还能通过文件系统打开一个很大的数据文件，完全不花上下文。6.1.3 节会说明两者的具体开销。

3.  **每沿着引用读取一次，就要多一轮。** 沿着引用打开文件，就要进行一次循环迭代；文件之间层层引用，会让任务增加很多轮。多数情况下，`SKILL.md` 直接引用所需文件就够了，不必再嵌套一层。因此正文适合写成一份资源索引：每份资源配一行简介，说明何时需要打开。

脚本通过普通文件系统访问同目录下的文件，路径解析要严格得多。解释器负责解析这些路径，路径不对就明确报错。只有模型根据正文拼出的第一条命令是未经检查器验证的字符串。

看完整个过程，还有两点值得记住。正文没有提到的脚本只是多余的文件，因为模型没有线索去调用它。此外，模型运行脚本时并不读取代码，对参数的了解完全来自正文中介绍脚本的那句话。正文描述有误，就会导致错误调用，执行过程本身也没有机制提前拦住这类错误。还要注意，加载和运行各需一次循环迭代，因此从用户提出请求到实际开始执行任务，要经过两轮完整的模型推理。将说明文字留在上下文之外、等到需要时再加载，也要付出这样的代价。

### 6.1.3 渐进式加载：按层级付费

上面的过程分阶段加载 Skill，到了哪个阶段，才承担相应的开销。这种做法叫渐进式加载，能让大量 Skill 随时可用，同时只让其中很小一部分占用上下文。

| 层级            | 内容                                     | 何时加载                     | 上下文开销                 |
|-----------------|------------------------------------------|------------------------------|----------------------------|
| 第 1 层：元数据 | frontmatter 里的 `name` 和 `description` | 启动时，对每个已安装的 Skill | 每个 Skill 约 100 个 token |
| 第 2 层：说明   | `SKILL.md` 的正文                        | 模型判定该 Skill 适用时      | 通常不到 5000 个 token     |
| 第 3 层：资源   | 附带的文件与脚本                         | 按正文引用使用具体文件时     | 使用前为零                 |

表中的开销差异说明了 Skill 的价值。安装三十个 Skill，常驻开销约三千个 token，相对较大的上下文窗口来说几乎可以忽略；额外开销只来自当前任务实际使用的内容。如果把这三十套流程都写进系统提示词，那么每次对话的每一轮都要承担全部流程的开销。

到了第 3 层，读取文件与运行脚本的开销明显不同，足以影响设计。读进来的参考文件进入窗口，按全文长度计费；跑起来的脚本留在磁盘上，只有它的输出进入窗口。一段五百行的校验逻辑，如果写成文字，只要留在窗口里就会持续产生开销，模型每次用到时还要重新推演；如果写成 Python 文件，上下文开销就只取决于输出长度，往往只有一行 `Validation passed`。据此，只有一个正确答案的步骤应写进脚本，需要判断的步骤用文字说明。

### 6.1.4 Skill 与工具

Skill 和工具看起来很像，了解 Skill 的运行机制之后，就可以进一步区分两者。两者都在模型权重之外，也都事先向模型提供介绍：工具提供参数 schema，Skill 提供描述，模型读过后再决定是否使用。即便某一轮没有用到，这些介绍也会占用上下文窗口。两者都由智能体在循环中使用，而不是模型内部的运算机制。

差别从模型选定之后开始：

|                  | 工具                                                              | Skill                                                                             |
|------------------|-------------------------------------------------------------------|-----------------------------------------------------------------------------------|
| 是什么           | 智能体可以调用的一个函数，带一份固定的参数表                      | 一个文件夹，装着说明，常常还有脚本和数据文件                                      |
| 使用时发生什么   | 智能体送出参数，代码在模型外部运行（第 3 章的陷入边界），结果返回 | 智能体读说明，然后用它已有的工具去把事做完，包括通过 shell 工具运行文件夹里的脚本 |
| 智能体得到什么   | 一个此前根本无法执行的动作                                        | 一套利用已有动作完成任务的现成方法                                                |
| 谁检查参数       | 运行时在代码执行前按 schema 校验                                  | 模型自己写参数，检查发生在接收参数的脚本内部                                      |
| 闲置时的代价     | 它的 schema，每一轮都待在上下文窗口里                             | 它的名字和描述，约 100 个 token                                                   |
| 新增一个要做什么 | 写代码、部署、向智能体注册                                        | 把一个文件夹复制到位                                                              |

一句话概括：**工具让智能体能做新的事；Skill 把它已有的工具编排起来完成一项任务。** 报销单 Skill 是个好例子。它调用的文件读取工具、表格工具和邮件工具原本就已具备，价值在于明确调用顺序、字段名，以及执行流程时要遵循的公司规则。

文件夹里的脚本看着像个例外，值得说清楚。脚本是一个文件，总得有东西去运行它：shell 工具，或者代码执行工具。智能体没有这类工具时，`scripts/` 里的脚本一个也无法运行；有这类工具时，本来就能运行任意程序，包括模型当场编写的程序。两种情况下，脚本都没有给智能体带来新的动作。脚本提供了一段事先编写并测试过的程序，用来替代模型临时编写的版本，既更可靠，也能减少完成任务所需的轮次。脚本通过 shell 工具运行，也要像智能体执行的其他命令一样接受权限检查。

谈到脚本，还需要说清楚 Skill 究竟依托什么运行。Skill 依托的是环境，而不是工具清单，包括文件系统、网络以及环境中已安装的解释器。Python 运行时不是工具，没有列入工具 schema，而是安装在容器里，由脚本通过 shell 调用。所以工具清单是门，环境是门后面那间屋子。shell 工具决定智能体能否运行程序，容器决定有哪些程序可用，两者都由部署者提供。Skill 能完成哪些任务，取决于环境提供哪些能力；工具清单则决定它能否访问这个环境。有些运行时允许在 frontmatter 中列出 Skill 可以使用的工具，明确限定执行这套流程时的可用范围。

## 6.2 不可小觑的细节

### 6.2.1 当脚本打开一个窗口

这里有两个问题，第二个要在第一个得到肯定回答后才有讨论的必要。Skill 的脚本能不能包含图形界面？如果能，这个界面能不能反过来给模型派活？

先看第一个。脚本可以像普通程序一样包含图形界面代码：引入工具库、定义窗口、将按钮绑定到处理函数，都是普通代码操作，不会因为放在 Skill 文件夹里就受到限制。能否显示图形界面，关键在于窗口能否运行，以及用户能否使用，而不只是有没有这段代码。这需要三个条件同时成立，而普通的 Skill 沙箱一个都不提供。绘制窗口需要屏幕，而沙箱是无头环境；窗口要等待用户点击，需要进程持续运行，而沙箱会在脚本运行结束、取得输出后终止进程；用户要操作窗口，还需要访问入口，而沙箱是封闭的，只有智能体运行时能够访问。因此在通常情况下，脚本即使创建了窗口，用户也无法看到或使用。专门搭建的环境可以逐一满足这些条件：通过用户可访问的端口提供界面，让工作进程在整个会话期间持续运行，再将事件送回循环。这样，窗口就能运行，也能供用户使用。可见，Skill 能否显示图形界面，取决于运行环境，而不是 Skill 本身。

窗口运行起来后，就可以讨论更关键的第二个问题。有人点击“总结这几行”，点击事件就变成一条输入模型的消息，与用户直接输入的请求完全一样，模型读到后便按指令执行。脚本没有在算出结果后结束，而是向模型发送指令，然后继续运行。原本是模型按说明调用脚本，现在脚本也会反过来向模型发送指令，调用变成了双向的。

脚本反过来给模型安排任务，超出了循环原本的设计：循环本来是在发起调用后等待结果，并不负责接收被调用程序安排的新工作。如果直接在主会话里执行这些任务，就会出现两个问题。控制权变得模糊：用户随时可以通过窗口加入任务，下一步做什么不再只由模型决定。上下文也会不断膨胀：每次点击和回复都累积在同一个上下文窗口里，操作时间一长，Skill 的说明就会被挤出去。模型还在接收点击事件，处理这些事件的规则却已不在上下文中。

解决这两个问题，可以引入外层编排循环，也就是智能体两层循环中的第二层：内层循环在一次运行中不断推进，直到模型没有进一步的请求；外层循环将子任务排好队，每个子任务都单独启动一次新的运行。外层循环留待后续进一步讨论，这里只看任务如何分发。把每一条进来的指令交给一个新的子智能体，而不是在主上下文里执行。点击事件仍会到达，但父智能体会启动子任务，由子任务加载当前指令所需的内容，生成摘要，返回简短结果。具体交互都在子任务内完成，父智能体只负责转发点击、收集答复。交互记录留在子任务里，也就不会挤占父智能体上下文中 Skill 核心说明的位置。

### 6.2.2 智能体没有作用域这回事

程序始终能明确区分数据属于哪个上下文，因为编程语言划定了边界。函数里声明的变量只在函数内部可见，类实例上的属性属于当前对象，不属于其他对象。函数的局部变量和常量保存在各自的栈帧里，与其他栈帧隔离，函数返回后就消失。这里的作用域同时决定两件事：哪些数据在哪里可见，以及一个值能保留多久。

智能体没有这些标记。无论是 Skill 的说明、一批结果，还是正文中的常量，模型读到的内容都会进入同一个上下文窗口，共用一个扁平的命名空间。于是当两个值同名时，没有任何东西把它们区分开。同一个词在窗口里出现两次，却没有办法明确区分各自的含义，因为这里没有“这次运行内部”或“这个 Skill 内部”这样的边界。

同名冲突有两种情况。第一种是同一个 Skill 运行两遍：处理 Q3 时写下一个 `total`，处理 Q4 时也写下一个 `total`，同一个名字对应两个值，只能靠周围的文字区分。第二种是两个不同的 Skill 使用同一个名字：应收账款 Skill 把 `overdue` 定为超过 90 天，客服 Skill 则定为超过 2 天，同一个名字的两种含义出现在同一个窗口里。程序本身就能避免这两种冲突：每次调用都有独立的栈帧，每个模块都有独立的命名空间。智能体两者都没有，因此同一个词可能对应两个不同的值或含义。

这种冲突会产生看似正确、实则有误的答案。模型多数时候能分清，出错时却往往不会报错，而是将两者混用：把 Q3 的数字列在 Q4 的标题下，或者把 90 天的规则用在客服工单上。输出没有任何警示，读起来仍然合乎情理，就这样交付出去，读者也无从察觉偏差。以下三种情况更容易导致混淆。

1.  **两个值长得像。** 名字相同、量级相仿，可供区分的线索就少。

2.  **这些值出现在较长上下文窗口的靠后位置。** 数值与来源信息相隔越远、中间内容越多，两者的联系就越弱。

3.  **周围的文字没有注明来源。** 以 `Total:` 开头的一段，既可指第一次运行，也可指第二次；而“overdue 就是 90 天”这样的规则没有注明适用范围，等于把这个词固定为一种含义。

可以通过外层编排循环，把任务交给具有独立上下文的子智能体。子任务加载 Skill，使用其中定义的名称，处理完当前批次，再返回一份带标签的简短摘要。这些名称只在子任务中使用，不会进入父智能体的命名空间；两批数据分别在两个子任务中处理，各用各的上下文窗口。智能体无法按作用域隔离，按进程隔离就是最接近栈帧的做法。

不过隔离也有代价，不适合作为默认选项。子任务无法读取父智能体的对话。按公司规范排版文档的 Skill 需要正在讨论的文档，报销单 Skill 需要四轮之前提到的收据；如果将这些任务隔离，调用方就得手动重新传入材料。子任务还要重新构建上下文，再次承担系统提示词、工具 schema 和 Skill 正文的开销，派发任务和收回结果也各需一次循环迭代。对于只运行一次、返回一段话的 Skill，这些开销反而超过了避免干扰所带来的收益。

因此，默认共用一个扁平的上下文更合适；只有确实需要让某些内容对后续任务不可见时，才考虑隔离。以下三种情况提示我们考虑隔离，但判断方法各不相同。

1.  **正文中仅适用于特定范围的常量。** 作者能够事先确定这些常量的适用范围，调用方却并不知道。作者清楚，正文将 `overdue` 定义为超过 90 天。这种定义应与名字一同写进 frontmatter，让智能体在读取正文之前就能从元数据中得知。

2.  **重复运行。** 通常从请求本身就能判断是否需要重复运行。例如，看到“对比 Q3 和 Q4”，还没开始执行就知道需要运行两遍。即便请求没有明说，也可以在第二次运行前决定：第一次已经完成，就把第二次放进子任务。

3.  **大体量输出。** 输出量取决于输入文件，无法仅凭 Skill 预判，可以采用两种处理办法。一是在源头封顶，让脚本把结果写进文件、只打印一行 `wrote 4,213 rows to /tmp/q3.csv`，这样不论输入长到多大，上下文占用都是固定的。二是事后清理：先运行 Skill，取得结果后，再从窗口中移除过长的工具返回结果，只保留摘要。这样无需事先决定是否拆分子任务，也能达到同样的上下文精简效果，代价是需要重新计算缓存，6.2.3 节会讨论这个问题。

其余大多数情况，只需养成一个成本很低的习惯：为每个值注明来源，写 `Q3 export — total` 而不是 `total`，写 `receivables overdue` 而不是 `overdue`。编译器会强制执行作用域规则，标签则只是由模型遵守的约定，约束力较弱，但几乎没有开销，也能应对大多数情况。隔离的成本较高，适合用于标签已经失效，或者不能满足于“多数时候是对的”的场合。

### 6.2.3 两种缓存代价

推理服务会缓存根据对话前缀算出的键值（KV）张量，后续请求如果共用这段前缀，就不必重新计算。这能节省大量计算，而使用 Skill 时，既有可以保留缓存的操作，也有会使缓存失效的操作。

对话中途加载 Skill 时，读取的内容作为工具返回结果追加到末尾，前面所有 token 的缓存都仍然有效。向长会话中加入四千个 token 的说明，开销与追加一条普通的工具返回结果差不多。

另外两种操作会修改前面的内容，开销也就更大。会话中途启用一个新 Skill，会改动第 1 层的元数据块。这部分内容位于系统提示词中，在对话最开头；一旦改动，后面整段对话的缓存就会失效，需要重新计算全部历史内容。移除内容也有同样的问题。通过上下文编辑，可以从窗口中间删除旧的 Skill 正文，但删除点之后所有 token 的缓存也会随之失效。腾出四千个 token 的空间，可能需要重新预填充十万个 token。因此，Skill 的正文一旦加载，往往就会一直留在上下文中。

如果需要回收这部分空间，可以通过外层编排循环安排子任务，而不在内层循环中修改上下文。这与 6.2.2 节用隔离来模拟作用域的办法相同。在一次全新的推理循环里启动子任务，只加载这个子任务需要的 Skill，返回结果而不是整段记录。父智能体的上下文只接收一段简短结果，不接收整份文档；加载 Skill 正文的子任务进程结束后，正文也随之释放。计算机选择“另起一个进程”还是“在运行中的进程里腾内存”时，也要做同样的权衡。

### 6.2.4 悄无声息的漏触发

Skill 该触发却没有触发时，不会留下任何提示。智能体仍会凭通用知识作答，口吻同样笃定，内容也看似合理，快速扫一眼很难发现问题。计算机遇到未解析符号时，加载器会停止并报出所需文件；Skill 漏触发却不会留下这样的痕迹。因此，要发现漏触发，需要检查对话记录中是否读取过 `SKILL.md`，而不能只从回答质量上寻找问题。

这种没有明确报错的机制，会出现三类触发问题。

1.  **触发不足。** 描述是用作者的说法写的，比如“生成季度差异分析工作簿”，而用户敲进来的是“给我做个 Q3 的表”。这个 Skill 虽然正确、完整，却始终无法触发。

2.  **触发过度。** 描述如果写成“任何文档类任务都可使用”，就会在各种任务中触发；每次误触发，都会为当前任务用不上的说明消耗数千个 token。

3.  **撞车。** 两个 Skill 的适用范围重叠，一个说“创建电子表格”，另一个说“分析表格数据”。模型选中一个后，这次选择就作为已完成的步骤写进上下文，看起来已成定论，后续处理同一任务时往往会一直沿用。

可以把描述看作一个分类器，按评估分类器的方法来检验。写下二三十种真实用户可能采用的说法，逐条运行，统计有多少条加载了目标 Skill，又有多少条加载了适用范围相近的其他 Skill。能清楚区分适用范围的描述，比仅仅准确说明用途的描述更有用。
