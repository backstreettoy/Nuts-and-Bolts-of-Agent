# 第三章 —— 内部工具调用

计算机靠陷入（trap）接触外部世界。程序把控制权交给内核，内核运行驱动，驱动让设备执行操作，随后控制权返回程序。智能体走的是同一条路，工具调用就是它的陷入：模型把控制权交给运行时（runtime），运行时执行工具，再把结果返回模型。两者的流程相同，但调用边界上有两处差异，本章就从这两点展开。

第一个变化是执行内容的变化。计算机中CPU执行的是根据严格规则编译后生成的二进制指令；在智能体里，模型看到的是普通的指令文档，模型做的就是根据输入的文档输出对应的文档。

第二个变化是出错的代价。在计算机里地址出错进程将马上终止，这类错误对进程是致命的，而内核则完全不受影响。在智能体里，调用失败的结果经序列化后也写入上下文，模型在下一轮迭代中读取，错误内容也就成了循环的一部分。正因为如此，智能体才能靠不断试探找到正确的答案。

这两个变化都源于工具调用来源于模型生成的文本。运行时因此要承担两项职责，划分方式与内核不同：既要检查每次调用的形式，也要决定合法调用能够访问和操作什么。本章以 `write_text_file` 为例，介绍从工具定义到返回结果的全过程。3.1 讲什么是工具，以及一次调用如何完成；3.2 进一步讨论工具集扩大后才逐渐显现的几个问题。

## 3.1 概念、目标与结构

工具让模型能够影响上下文窗口之外的事物。模型只产出文本，工具把其中特定的文本变成动作，再把结果带回来。内部工具（internal tool）是运行时直接提供的那一小组固定工具，本章只谈内部工具，外部工具是在内部工具基础上增加了远程方法调用（RPC）扩展，故不在本书中涉及。至于按需从存储加载的Skill则留到第 6 章。这一组工具按方向分成两类。**读取类工具**把数据读进来，包括读文件、列目录、抓网页，读错一次模型可以根据返回的观察结果纠正。**动作类工具**把数据写出去，包括写文件、改文件、执行命令，做错一次外部环境就会改变，有些改动还会保留下来。两类工具出错的后果不同，需要的保护也不同，所以本章选用动作类工具 `write_text_file` 作为例子，基于这个例子介绍工具调用的全过程。

### 3.1.1 工具由什么构成

每次调用都涉及三方，各有分工：

1.  **模型**提出调用，以结构化输出给出工具名和参数，然后等待结果。
2.  **运行时**（runtime）决定是否允许调用，并负责执行流程，运行时是在承载框架中的一个模块，这个模块主要的功能是支持**推理循环**（inference loop）运行，针对推理循环的详细介绍放在下一章。其主要功能是解析调用、检查参数、落实权限限制、运行工具，再把结果转换成模型能读的文本。
3.  **工具**在模型的上下文之外，按自身的执行流程完成操作。

模型提出调用请求，运行时裁决是否允许执行。模型在提出调用请求时会生成对应工具名和参数，这些通常是一份JSON格式的文本。运行时根据这些信息加上工具的配置决定是否允许工具执行，如果能够放行，则运行时会调用对应的工具得到结果。因此，智能体能访问和操作什么、不能访问和操作什么都由运行时来保证。

一份工具定义分为两部分，分别供模型和运行时使用，存放的位置也不同。**面向模型的那一半**进入上下文窗口，回答模型关心的问题：什么时候调用这个工具，用什么参数。

``` sourceCode
{
  "name": "write_text_file",
  "description": "Write text content to a file on the local disk, creating
                  the file or replacing its content. Use append: true to add
                  to the end instead. For changing part of an existing file,
                  use edit_file. For binary data, use bash.",
  "input_schema": {
    "type": "object",
    "properties": {
      "path":    { "type": "string",
                   "description": "File path, absolute or relative to the
                                   working directory, e.g. notes/summary.md" },
      "content": { "type": "string",
                   "description": "The full text to write" },
      "append":  { "type": "boolean", "default": false,
                   "description": "Add to the end instead of replacing" },
      "encoding": { "type": "string", "default": "utf-8",
                    "enum": ["utf-8", "utf-16", "ascii"] },
      "create_parents": { "type": "boolean", "default": false,
                          "description": "Create missing parent directories" },
      "dry_run": { "type": "boolean", "default": false,
                   "description": "Report what would be written, and write
                                   nothing" }
    },
    "required": ["path", "content"]
  }
}
```

其中有四项主要内容：

1.  **`name`** 是工具的唯一名称，运行时据此精确查表，模型则要一字不差地输出工具名。名称简短、以动词开头，模型生成时就更不容易出错。
2.  **`description`** 是分发逻辑，因为模型要根据描述选择工具。描述要说清楚这个工具做什么、什么时候用，以及什么时候用另一个工具更合适；对 `edit_file` 的交叉引用明确了两个工具各自的适用范围，3.2 会说明这句话能避免什么错误。
3.  **类型**让运行时有据可查：参数可以是布尔值、含三种编码的枚举，或附有示例的字符串。相比抽象的类型名，`notes/summary.md` 这样的具体例子更便于模型仿照，也更不容易出错。
4.  **必填与带默认值**区分了参数的生成代价。`path` 和 `content` 每次调用都要生成；另外四个可以省略，由运行时填入默认值，不增加生成参数的代价。

**面向运行时的那一半**留在上下文窗口之外，回答的是另一个问题：允许这个工具访问和操作什么。

``` sourceCode
{
  "effect": "mutate",
  "sandbox": {
    "allowed_paths": ["/home/user/workspace/**", "/tmp/agent/**"],
    "denied_paths":  ["**/.git/objects/**", "**/.env", "**/id_rsa*"]
  },
  "confirmation": {
    "on_create": "allow",
    "on_overwrite": "ask",
    "outside_allowed_paths": "ask",
    "above_bytes": 10485760,
    "grants": "session"
  },
  "reversal": { "strategy": "backup_before_overwrite",
                "backup_dir": "/tmp/agent/undo" },
  "limits": { "timeout_seconds": 10, "max_content_bytes": 52428800 }
}
```

确认层级按一次调用可能造成的破坏来定。新建文件不会破坏已有内容，可以直接放行；覆盖文件会替换原有内容，需要先暂停调用，把改动展示给用户；写入允许范围之外，或者超过大小上限，同样要暂停。`grants: "session"` 表示一次批准在本次会话中，对指定工具和路径模式持续有效，这样就不必为同一范围内的调用反复确认。将定义分成两部分，是出于安全考虑：**模型读第一半，运行时执行第二半。** 模型读到的文本可能改变它的判断，所以约束要放在模型既读不到也改不了的代码里。两部分缺一不可，合在一起才是一份完整的工具定义；权限门、沙箱和确认对话，第 5 章会详细介绍。只有面向模型的部分占用上下文，权限表无论按需扩展到多大，都不会增加上下文开销。

### 3.1.2 一次调用怎么跑完

面向模型的那一半随推理请求一起发送，作为请求中的一个参数。在 OpenAI 的 chat API 里，这部分内容放在 `tools` 字段中，每个已注册的工具对应一个条目，条目里的各个值都来自上述定义：

``` sourceCode
POST /v1/chat/completions
{
  "model": "…",
  "messages": [
    { "role": "system",    "content": "…" },
    { "role": "user",      "content": "summarize README.md into
                                       notes/summary.md" }
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "write_text_file",
        "description": "Write text content to a file on the local disk,
                        creating the file or replacing its content. Use
                        append: true to add to the end instead. For changing
                        part of an existing file, use edit_file. For binary
                        data, use bash.",
        "parameters": { "type": "object",
                        "properties": { "path": …, "content": …,
                                        "append": …, "encoding": …,
                                        "create_parents": …, "dry_run": … },
                        "required": ["path", "content"] }
      }
    },
    { "type": "function", "function": { "name": "read_file", … } },
    { "type": "function", "function": { "name": "edit_file", … } }
  ]
}
```

字段的对应关系很直接：`name` 和 `description` 原样保留，`input_schema` 改为 `parameters`。面向运行时的那一半不出现在请求中，而是留在运行时，由运行时强制执行其中的沙箱、确认层级和回退策略。每次推理都要重新发送 `tools` 里的全部条目，注册表越大，占用的上下文就越多。模型输出一次工具调用后，运行时便接手处理：

    模型输出：  {"name": "write_text_file",
                "input": {"path": "notes/summary.md",
                          "content": "# Summary\n..."}}

    调用路径     1 从模型输出里解析出这次调用
    （运行时）   2 在注册表里查这个名字
                3 按 input_schema 校验参数
                4 填默认值，把取值规范化
                5 检查工具自身的前置条件
                6 检查权限                  ← 面向运行时的那一半
    执行         7 先备份，再在超时限制下运行
    返回路径     8 采集结果
    （运行时）   9 标记成功或失败
               10 把结果压小
               11 把结果块追加到上下文

    下一次推理：模型读到结果，决定下一步

调用路径分为六个检查阶段，各自拦截不同类型的错误：

1.  **解析。** 运行时提取结构化的调用。模型通过专门的通道发出工具调用，因此这一阶段很可靠。
2.  **查名。** 在注册表中精确匹配工具名。查不到就返回可用的名称，模型在下一轮迭代中自行改正。
3.  **schema 校验。** 检查类型、必填字段、枚举取值和边界。发现不符合要求的参数，就报出参数名、期望类型和收到的值：`parameter "append": expected boolean, received "yes"`。更严格的做法是在生成阶段就由运行时约束采样，让模型只能产出符合 schema 的调用，这样就只剩下“格式合法但语义不对”这一类错误。
4.  **默认值与规范化。** 为省略的参数填入声明的默认值，再将 `notes/summary.md` 解析成 `/home/user/workspace/notes/summary.md`。运行时只规范形式，不改意图：把字符串 `"yes"` 强转成布尔值，会掩盖参数使用上的混淆，清楚的报错则能把问题指出来。
5.  **前置条件。** 工具检查自己适不适用，并说出改法：`parent directory /home/user/workspace/notes does not exist; pass create_parents: true to create it`。
6.  **权限。** 运行时读取面向自己的那部分定义，按确认层级执行相应规则。例子里那次调用是在工作区内新建文件，可以直接放行；同样的调用如果要写入已有文件，就会暂停并展示改动。权限检查必须放在规范化之后，因为只有这时才能确定实际使用的路径。

执行时先备份已有内容，再在超时限制内写入。这里需要超时限制，是因为一次调用卡住就会阻塞整个循环：结果只能在循环边界返回，正在进行的回合没有可用的抢占机制。循环本身留到第 4 章。

返回路径把一次执行的结果变成一条观察结果：

    <tool_result name="write_text_file" id="call_7" status="ok">
      wrote 412 bytes to /home/user/workspace/notes/summary.md (new file)
      backup: none (file did not exist)
    </tool_result>

这个结果块有三处关键细节。标识符 `call_7` 将结果与对应的调用关联起来，一个回合同时发出多次调用时，就能据此区分各自的结果。显式的状态位直接表明调用成功，模型无需自行推断。正文报告本次改动的实际情况，无需再次回显刚写入的文本，因为那段文本已经在模型的上下文中。

结果按大小采用同一套处理策略：小结果完整返回；中等结果保留头尾，并在中间加上标记，说明省略了什么，例如 `[... 4,200 lines omitted ...]`；大结果保存在运行时的存储中，工具只返回一个句柄，例如 `[full log at tool_call:abc123]`，并说明所存内容的类型和结构。第 2 章把上下文窗口称为稀缺资源，工具是否节省上下文，取决于这里如何处理结果。保留句柄后，裁剪掉的内容仍可取回；使用句柄需要付出什么代价，3.2 会接着说明。

下面用一个任务展示完整流程。用户说：*把 README.md 总结到 notes/summary.md*。模型没见过这台机器，只能先按假设行动，再根据返回的观察结果修正假设。

    第 1 轮  read_file: README.md
            → 原文内容
    第 2 轮  write_text_file: path="notes/summary.md", content="# Summary…"
            → 报错：parent directory /home/user/workspace/notes does not
              exist; pass create_parents: true to create it
    第 3 轮  write_text_file: path="notes/summary.md", content="# Summary…",
                             create_parents=true
            → ok：写入 412 字节（新文件）
    第 4 轮  read_file: notes/summary.md
            → 内容确认

模型原先假设目录存在，工具报错并给出改法，模型在第 3 轮据此调整调用；错误以数据形式返回，由循环完成处理。第 4 轮检查执行后的结果：先运行动作类工具，再读取改动后的内容。程序员会把这些检查提前写进脚本，智能体则在运行时根据观察结果决定如何检查。这样虽然多了几个步骤，却能适应脚本未曾预料到的机器环境。

## 3.2 不可小觑的细节

如果只有几个工具、每次发出一个调用时，上面这套机制可以运转良好。随着结果增大、工具清单变长，下列四个问题逐渐显现，每一个都容易描述却不容易解决。

### 3.2.1 渐进披露的内部实现

第 2 章从上下文的角度介绍过渐进披露（progressive disclosure）：窗口里放一份压缩后的摘要，需要回答具体问题时，再取回原始文档。取回文档需要一次工具调用，具体做法是把长文档留在磁盘上，只将几行摘要放进上下文。如果某一行还有进一步的内容，就在行末加上标记，注明内容所在的文件。这个标记代表一项长期有效的约定：`[more detail, filename]` 表示全文在指定文件中，模型可以自行读取。

例如，运行时读过一份很长的天气报告后，将内容压缩为简短的摘要：

    Tomorrow is suitable for hiking. [more detail, weather.txt]

这一行足够回答大部分问题。但如果用户问要不要带雨衣，摘要里的信息就不够了，模型便调用内部工具 `read_file` 读取文件：

    <tool_use name="read_file" id="call_3">
      { "path": "weather.txt" }
    </tool_use>

承载框架（harness）执行这次调用，读取文件并将内容放入上下文：

    <tool_result name="read_file" id="call_3" status="ok">
      Tomorrow: high 22C, low 14C.
      Wind 10 km/h from the west.
      Rain chance 20% before noon, 5% after.
      Sunrise 06:12, sunset 19:40.
    </tool_result>

有了这些细节，模型就能回答了。是否加载细节，取决于回答问题的需要，而不是文档的长短。这种做法有两处关键安排：一是标记中给出真实文件名，模型只需照抄名称，无需推算；二是标记前的摘要已经点明“明天”“徒步”这两个主题，模型不用打开文件，就能判断是否值得读取。如果只写“详见报告”，模型就只能把报告全部打开后再作判断。

### 3.2.2 正确的参数调用了错误的工具

有两类失败的代价很低：工具名无法识别，会在第 2 阶段拦下；参数不合规，会在第 3 阶段拦下。两种情况都会返回报错并指明改法，一轮迭代就能修正。第三类失败的代价则高得多。

任务是改配置文件里的一行。模型调用 `write_text_file`，把改好的那一行作为 `content` 传进去。每一道检查都通过：名字存在，参数符合 schema，路径落在沙箱之内。于是工具用 63 个字节替换掉了一个 14000 字节的文件，完全按照指令执行。这类错误难以处理，因为校验找不到不合规的地方：调用格式正确，工具也按要求完成了操作，问题在于这次调用不符合任务意图，而意图恰恰是 schema 描述不了的。下面三道防线分别作用于不同层次，可以降低这类错误的发生频率：

1.  **用描述划清适用范围。** “for changing part of an existing file, use edit_file” 这句话正是为了防止上述误用。描述本身就是分发逻辑，修改描述也是代价最低的补救办法。
2.  **由工具检查可疑操作。** 在第 5 阶段加一条前置条件，让工具比较写入前后的内容大小：如果一次调用要用很少的内容替换一个大文件，就报出 `target holds 14,000 bytes; this call leaves 63; for a partial change use edit_file; to proceed, repeat with confirm_replace: true`。
3.  **通过覆盖确认拦截遗漏的错误。** 替换已有文件前先暂停，等待用户确认，让用户在损失发生之前就能看到改动。

这个例子说明：**只有错误造成的后果可以承受，才能把它当作观察结果，在后续调用中纠正。** 读错一次，代价是一轮迭代；覆盖错一次，代价是原有文件内容丢失，而且报告要在损失发生后才返回。动作类工具因此需要备份策略，确认层级也要按“会破坏什么”来划分，而不是看文件显得有多重要。第 5 章会介绍负责执行这套规则的权限门。

### 3.2.3 越长越大的工具列表

工具从八个增加到八十个，会增加两类代价，需要分别考虑：

1.  **上下文代价。** 面向模型的那一半只要常驻，每次推理就要重读一遍；注册表越大，在模型开始处理任务之前，占用的上下文空间就越多。
2.  **选择代价。** 模型根据文字描述选择工具，描述越多，越容易互相干扰。如果六份描述都在讲写文件，工具之间的适用范围就难以区分，上面说过的各类失败也更容易发生。

有两种方法可以减少常驻上下文中的工具信息。分层定义只为每个工具保留一行摘要，等模型考虑使用某个工具时，再加载完整定义。按任务划分工具集，则只为子任务提供所需的工具：调研环节使用读取类工具，构建环节使用 shell 和 `write_text_file`。第 7 章会介绍负责分配工具的外层循环。这两种方法都能降低代价，但工具选择的问题依然存在，而且并不容易解决。

### 3.2.4 分发难题：一层、多层，还是更宽的工具

面对八十个工具，有三种组织方式，各有代价。这一小节会详细比较，因为没有哪种方式可以免去所有代价。

**一层**只需要做一次分发决定：从八十条彼此干扰的描述中选择一条。假设描述之间的干扰使选择准确率降到 90%，模型就要在这些干扰下完成选择；一旦选错，下一步便会失败，也能直接追溯到这次选择。

**多层**将工具组织成一棵树，每层只需五选一，选择范围更小，也更容易区分。单层准确率虽然提高了，总体准确率却要由各层的准确率相乘。三层各 97%，0.97³ ≈ 91%，只比一层的 90% 高一点点。三层各 95%，得 86%，反而更低。要让新增的一层带来收益，就必须采用模型几乎不会判断错的分类方式，例如区分本地文件和网络。增加深度还会带来另一项代价：**树越深，错误越晚暴露。** 如果在顶层选错分支，后续选择仍可能看起来都合理。第二层和第三层都可能在错误的子树中作出正确选择，直到叶子节点，甚至整个任务结束时，问题才显现。平铺的工具菜单在选错后即可报错，树形结构则可能延迟暴露错误；层次越深，纠正错误时需要回退的步骤也越多。

**更宽的工具**采用第三种方式：将新能力做成可选参数，纳入已有工具，而不是增加一个工具。这种方式几乎不增加代价，原因在于带默认值的参数在用到之前无需生成，分发时又只读取摘要，因此模型选定工具后才需要确定参数，不必在选择工具时一并考虑。扩展单个工具的代价，只在调用该工具时承担；增加工具数量的代价，则在每次选择工具时都要承担。

工具也不能无限加宽，可以用动词来判断何时该停止。`append` 只是改变了工具执行 *写* 这一动作的方式，因此适合做成参数。而 `mode: "delete"` 这样的参数会把两个动词放进同一条描述；一旦描述涵盖互不相干的操作，每种操作的特征就更难突出。一种可能的解释是，混杂的内容分散了模型的注意力。具体机制仍是尚未解决的研究问题，但实践中可以观察到选择错误增多，因此这条设计规则仍然成立。判断方法是：**只要工具的一行摘要无需加上“和”来连接另一种操作，这个参数就仍属于这个工具。**

| 组织方式           | 收益                                                     | 代价                                                               | 适用条件                                                                   |
|--------------------|----------------------------------------------------------|--------------------------------------------------------------------|----------------------------------------------------------------------------|
| **更宽的工具**     | 以很低的代价扩展能力；选定工具后才确定参数，菜单大小不变 | 只能围绕一个动词；用模式开关打包多种操作，会使各模式的特征更难突出 | 新能力只是改变工具已有动作的执行方式                                       |
| **更多工具，一层** | 描述之间的适用范围清晰；选错后，下一步就会暴露问题       | 每个工具都会增加每次推理的上下文开销；描述互相干扰时，准确率会下降 | 新能力对应一个新动词，且菜单仍便于区分，大致在二三十个工具以内             |
| **更多层**         | 每次选择的范围小、易于区分；可容纳几百个工具             | 各层准确率相乘；错误到叶子节点才暴露，层次越深，回退步骤越多       | 平铺菜单已难以区分，但存在模型几乎不会判断错的分类方式，且每层都有退出路径 |

表中的选择顺序是：一行摘要仍能概括，就扩展现有工具；菜单仍清晰，就增加工具；只有存在几乎不会判断错的分类方式时，才增加一层。每种组织方式都有适用限度，只要不超出这个限度，就是合理的选择。如果注册表始终很小，平铺仍然是最好的安排。
