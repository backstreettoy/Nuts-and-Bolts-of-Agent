# 第二章——上下文

智能体需要管理上下文，是因为模型不会自动记住上一次请求中的对话。要让任务连续进行，智能体必须把对话保存在模型之外，并在每次请求时重新提供所需的内容。本章讨论的就是这份外部记忆，以及智能体如何管理它。

处理器带着状态往前走。寄存器和内存里的值从一条指令保留到下一条指令，保存着的值可以凭地址再次取出。工作内存不必随着每条指令重新建立，处理器需要时直接读取即可。智能体的核心则是一个大语言**模型**（model）：它读入一段输入，产生一段输出，却不会自行把这次对话延续到下一次独立请求中。要接着往下做，仍需外部程序提供此前的内容。电影《记忆碎片》（*Memento*）在一个人身上呈现了类似的状况：主角丧失了形成新记忆的能力，只能靠自己留下的字条，每次重新拼出自己的处境。

这种差异带来了上下文管理的核心问题。要让模型接着此前的对话回答，智能体必须在每次请求中提供相关历史。模型的工作内存是一份视图，由外部程序在每次请求时重新构建，并不是模型自行保存的存档。模型是智能体的CPU，**上下文**（context）是它的工作内存，而完整记录放在 **外部存储**（store）里并不会全部放入上下文。本章始终围绕内存与上下文的差异展开。

## 2.1 概念、目标与结构

上下文是智能体在一次请求里送给模型的全部内容。模型在这一步能直接读取的任务信息都在其中，因此可以把上下文看作模型当前的工作内存。上下文的容量有上限，而对话却一直在变长。容量以 token 计量，token 是模型处理文本的基本单位，可以对应一个词、词的一部分或一个字符。随着对话增长，完整的**会话记录**（transcript）迟早会超出上下文的容量，承载框架必须决定每次放入哪些内容。**承载框架**（harness）是模型外面那层程序：它从智能体能使用的外部存储中找出需要的文件与会话记录组装每一次请求调用模型，再处理模型返回的结果。这项挑选工作就是**上下文工程**（context engineering）：为每次请求决定什么进入上下文，什么留在外面。

模型在独立请求之间不自行保存对话状态：接收输入然后返回输出，下一次调用仍要靠承载框架处理传入所需的内容。因此，承载框架发送的不只是当前请求，还包括与之相关的历史。对话较短时可以把完整历史一并发送；对话变长后就需要有所取舍。这里讨论的会话内容以文本形式保存，人可以直接阅读，存储、修改和传递也都方便。同一段对话的文本内容可以交给另一个模型、另一个版本，甚至另一家厂商。程序员可能会问：为什么不像其他长期运行的系统那样，把状态留在服务端，来回只传一个短小的句柄？在细节讨论中将回应这个疑问。

承载框架在上下文和更大的外部存储之间调配内容。存储里放着完整的会话记录，以及智能体能够访问的文件；承载框架把需要的数据调入上下文，也把暂时不需要的内容移出，腾出空间。移出时有两种做法：一种是在原位置留一条短标记，需要时凭标记取回原文；另一种是把长段内容压成较短的摘要，保留要点，省去细节。摘要通常需要再次调用模型，由模型读完原文，再概括成几句话。承载框架处理这些内容时，常以**块**（chunk）为单位。块是一段意思完整、可以独立理解的内容，例如一个段落或一条结果。本书把调入和移出这两个动作称为**换入**（paging in）和**换出**（paging out），借用的是操作系统虚拟内存在内存与外部存储之间搬移数据的说法。在智能体领域，换入通常涉及检索（retrieval），换出则可以采用压实（compaction）、修剪（pruning）或摘要（summarization）等做法。这些方法的具体机制有所不同，但都服务于同一个目标：在有限的上下文中安排当前所需的信息。

换出时留下的标记，还可以扩展成一套组织信息的方法：**渐进式披露**（progressive disclosure）。上下文先保留简短说明和指向完整内容的句柄，例如 `[full log at tool_call:abc123]`。说明告诉模型移走了什么，句柄则提供取回内容的地址。模型先读概览，任务需要时再取回细节，不必一开始就加载全部材料。对于无法一次装入上下文的大份资料，这是一种可行的安排。接下来“不可小觑的细节”一节将讨论：承载框架根据什么决定换出哪些内容，怎样组织庞大的结构化资料，让模型逐层查看，以及怎样搜索上下文之外的内容。

## 2.2 不可小觑的细节

上下文管理涉及几个不同的问题。这一节依次讨论：记忆采用什么形式，内容以哪些方式离开上下文，怎样分层才能让模型按需读取外部资料，以及怎样搜索尚未进入上下文的内容。

### 2.2.1 为什么会话记录是纯文本

许多长期运行的系统会把状态保存在服务端，客户端只持有一个短小的标识：数据库的一行凭主键查找，登录会话凭会话 ID 识别，打开的文件凭描述符访问。客户端只需传递少量数据，就能访问另一端保存的状态。智能体却常常在每次请求时重新提交上下文，并为输入的 token 付费。要理解这种做法，可以沿用键和值的类比：会话文本相当于重建模型状态的键，读取文本后形成的内部状态则是值。

从这个角度看，会话记录不仅承载对话内容，也提供了重建模型状态的依据。对于给定的模型和推理设置，读入哪些 token、按什么顺序读，决定了模型如何处理这段历史。每个 token 都参与这个过程，删去其中一部分，就不能保证重建出原来的状态。短句柄当然可以指向已经保存的状态，但前提是服务端仍然保存着它；句柄本身并不包含重建这份状态所需的信息。

数据库把行存下来，用时按键查找；模型则可以根据文本重新计算所需的状态。若要直接保存模型读取文本后形成的计算结果，主要需要保留的是 KV 缓存，也就是每个 token 留供后续计算读取的键和值向量。在某些大型开源模型的配置下，每个 token 的 KV 缓存要占几百 KB，一段一万 token 的对话，作为文本只占几十 KB，缓存却可能占几个 GB。KV 缓存依赖生成它的模型权重和计算配置，不能直接交给另一个模型使用；若从输入中间删去一段，后续缓存通常也需要重新计算。文本体积小、便于修改和传递，缓存体积大，又依赖具体模型，这使得保存文本、按需重建状态成为一种实用的选择。第七章会进一步讨论这项取舍。

用一个紧凑状态代表全部历史的思路，在循环神经网络中就出现过。循环神经网络保留一个固定大小的隐向量，每读入一个 token，就更新这个向量，再继续处理下一个，无须为每个已读位置保留一份表示。这个向量概括了此前的历史，代价是网络必须在读入时决定保留什么，而那时还不知道后面会遇到什么问题。Transformer 则保留此前各个位置的表示，让后续计算通过注意力读取所需的信息，把一部分取舍留到读取时再做。但上下文的容量终究有限，历史太长时，仍然要在未来的问题到来之前决定保留什么。这个老问题于是交给了承载框架，成为换出时必须处理的工作。

提示词缓存保存的是已经算好的状态，能否复用则取决于本次输入与此前输入是否匹配。服务端把计算结果保留一段时间，如果下一次请求有相同的开头，就可以通过前缀匹配复用相应的缓存。沿用前面的类比，键的前缀对应着值的前缀。在这种由客户端提交上下文的接口中，文本仍需发送，缓存减少的是重复计算。会话文本仍然是重建状态的依据，缓存则让已经完成的计算不必再做一遍。

### 2.2.2 压缩，以及把内容带回来的那条标记

上下文接近容量上限时，承载框架就需要移出暂时不需要的内容，腾出空间。常见的两种做法是保留摘要，或者保留能够取回原文的标记。区别在于，当前上下文里留下的是内容的概括，还是指向完整内容的入口。

压缩把上下文中的一长段会话记录换成较短的摘要。子任务完成后，相应的过程记录就可以缩成几句话；冗长的探索已有结论，或长篇工具结果已经用于指导行动时，也可以只保留结论，省去细节。摘要通常由一次模型调用来写，因为判断什么重要需要理解。压缩适合那些需要保留意思、暂时不必保留原话的内容：“我们试了 A，在时区这个用例上失败了，所以选了 B”压成“选 B 不选 A；A 在时区边界上会挂”，仍保留了选择结果及其原因。压缩是有损的，仅凭摘要无法还原所有细节；如果后续步骤需要原话，就必须重新查阅外部保存的完整记录。因此，承载框架应在判断细节暂时可以移出上下文时才做压缩。摘要若漏掉后续步骤需要的信息，智能体就可能据此作出错误判断，而且不容易察觉。

带标记的丢弃，则把取回原文的入口留在上下文里。这里的“丢弃”只指从当前上下文中移除，原文仍完整保存在外部。承载框架把内容移走，在原位置留下一条短标记，也就是说明内容去向的句柄，例如 `[full log at tool_call:abc123]` 或 `[file: report.md]`。这条标记有两个作用：提醒模型，当前上下文只保留了部分内容；提供地址，便于需要时取回移出的原文。

按标记取回内容，是换入中较容易的一种情况。后续步骤需要这些内容时，承载框架就按标记中的地址，将完整内容原样换回上下文。地址已经确定，只需精确查找，无须另行搜索。很多时候，这一步由模型发起：模型读到标记，判断当前任务需要细节，便请求取回，承载框架再执行读取。原文没有丢失，取回它所需的地址也留在上下文中。

两种做法如何选择，主要看后续更需要原文，还是只需要大意。一份文件、一条精确结果、一个标识符，如果之后还可能逐字核对，就适合保留标记，以便原样取回；一条推理线索、一段已有定论的讨论，如果只需知道结论和原因，就适合压缩成摘要。区分这两类需求，能让有限的上下文承载较长的历史，同时保住重要信息。

### 2.2.3 渐进式披露

标记使模型能够沿着引用，按需取回内容。渐进式披露把这种做法扩展到了整套资料的组织方式中。

智能体需要的材料里，有一部分是已知的，也有清楚的结构，只是无法一次装入上下文：一份代码库、一本长手册、一份 API 参考，或者智能体自己的技能集合。模型可能用到其中任何一部分，却通常不需要一次全部加载。这时，单靠相似度搜索往往不够，因为模型未必已经知道要找什么，也就难以准确描述需求。它需要先了解资料的整体结构，再选择要查看的部分。

渐进式披露的办法是把信息分层。最上面一层很小，始终留在上下文中，例如一份文件列表、一页目录、每个技能的一行说明，或者可用工具的名称。这份概览里的每一项都是一个引用，模型沿着引用就能读取下一层：打开一个文件，读一节内容，加载一个技能的完整说明，或者获取一个工具的完整定义。下一层若还有引用，就继续向下查看；模型只加载沿途需要的内容，不必把整棵树装入上下文。技能的加载过程很能说明这一点：没有任务需要某个技能时，上下文只保留该技能的名称和一句说明；有任务需要时，才加载完整说明。说明中引用的参考文件，也等到需要时再读取。概览始终简短，细节按需进入。

渐进式披露与搜索的区别，在于如何查找内容。搜索从需求描述出发，寻找匹配的材料；渐进式披露则从已有概览出发，沿着明确的引用逐层查看。引用提供了具体地址，模型可以直接访问相应的内容，难处也就转移到了信息如何分层上。概览要提供足够的信息，让模型选对分支，同时又要足够简短，才能常驻上下文。说明含糊，模型就可能选错分支，或者不得不逐一打开所有分支，才能判断该看哪一部分。决定什么放进概览、什么留到下一层，本身就是上下文工程。技能也依赖这样的组织方式，后面会有一章专门讨论。

### 2.2.4 为什么找到对的内容很难

按标记取回内容和渐进式披露，都依赖已有的线索：标记指向此前移出的原文，概览则给出事先组织好的结构。但智能体需要的内容，未必都有现成的地址或目录入口。一长串 DNA 序列没有标题可列，摘要也不能替代确切的碱基序列。一周里零散记录的日志中，要紧的几行可能混在几千行普通记录之间，仅凭目录很难知道它们在哪里。这类任务需要直接找到原始内容，承载框架往往只有一段需求描述，还不知道所需片段的具体位置，因此必须通过搜索将它们换入上下文。

换出与这种需要搜索的换入，难度并不相同。换出时，内容已经在上下文里，承载框架需要判断哪些可以移走；换入时，却可能只有需求描述，要从无法全部读完的大量资料中找到对应的内容。搜索的质量，决定了模型能否看到它需要的信息。

判断一次请求该用哪种搜索，可以先问两个问题。

1.  这次请求能否独立理解，还是必须结合前文？“我选第二个”这样的请求，要看前面的对话才知道具体所指，承载框架应先把它改写成能够独立理解的形式，再进行检索。已经明确主题的请求，可以直接用于检索。

2.  请求明确之后，提供的是精确字符串，还是对某种意思的描述？错误码、文件名、版本号等精确字符串，适合通过关键词检索匹配；用户用自己的话描述需求时，则可以通过向量检索，寻找语义接近的内容。

这两个问题可以帮助承载框架区分检索需求。简单请求往往用一种方法就能处理，实际消息却可能同时包含多个需求，需要分别处理。下面四个例子依次说明精确字符串匹配、语义匹配、消解指代，以及三者如何配合。

**1. 一个精确字符串：“我一直碰到 error 12345。”** 这个请求可以独立理解，也给出了明确的错误码，适合优先使用关键词检索，寻找包含同一字符串的块。一种经典方法是词频–逆文档频率（Term Frequency–Inverse Document Frequency，TF-IDF）：根据块与查询共有的词打分，其中罕见词的权重较高。假设“12345”几乎不出现在其他地方，那么曾经讨论这个错误的块就会获得较高得分，排到前面。只按语义相似度检索，未必能稳定地区分“12345”和“12346”这样的错误码。对于错误码、文件名、函数名和版本串，匹配到准确的字符串尤其重要。

**2. 一段描述出来的问题：“登录那个错误又回来了。”** 用户用自己的话描述了问题，其中“登录错误”已经提供了可用于检索的语义线索。存储中的相关内容却可能用了另一种说法，例如某个块写的是“认证一直拒绝有效的会话”。查询与这个块没有共同的关键词，单靠关键词检索就容易漏掉。向量检索可以弥补这类不足：每个块都经嵌入模型编码，在向量空间中表示为一个点；请求也用同样的方法编码，再由检索系统根据距离选出接近的块。“登录那个错误”与“认证拒绝会话”虽然措辞不同，仍可能在向量空间中彼此接近。两种方法各有所长：关键词检索适合准确的字符串，向量检索适合表述不同而意思相近的内容。至于“那个”“又”究竟指向哪一次错误，还需要结合对话历史，这就涉及下一个例子中的指代问题。

**3. 一个依赖上文的请求：“我选第二个。”** 这句话单独拿出来，几乎没有可用于检索的信息。“第二个”也许指智能体几个回合前列出的三个 Web 框架，不先弄清所指，关键词检索和向量检索都难以找到有用的结果。因此，承载框架需要先把请求改写成能够独立理解的形式。假设相关列表仍在最近几个回合中，承载框架就把这几轮对话连同新请求一起交给模型，通过一次快速调用消解指代。模型将“第二个”与列表对照，确认第二个框架是 FastAPI，便把请求改写成“我选 FastAPI，你列的三个框架里的第二个”。“那个”“同一个错误”“和上次一样”等说法，也可以在找到对应内容后，替换为明确的对象。改写后的请求有了具体的检索词，也表达了完整的意思，便可以交给关键词检索、向量检索，或者两者共同处理。如果指代对象已经不在近期窗口内，还需要查找更早的记录，或向用户确认。

**4. 一个混合请求。** 实际消息往往同时包含上述几种需求。假设用户写道：“你推荐的第二个框架还是抛 error 12345——这是不是我们上次碰到的那个认证问题？”这里包含三种不同的检索需求：“你推荐的第二个框架”需要结合前文消解指代；“error 12345”适合做关键词检索；“我们上次碰到的那个认证问题”则提供了语义线索，同时也带有对历史的引用。承载框架需要分阶段处理。

1.  先改写。结合最近几个回合，确定“你推荐的第二个框架”所指的框架。如果近期对话也能明确“上次”的具体所指，就一并补全；尚不能确定的历史问题，则保留现有线索，继续查找。

2.  将改写后的请求拆成若干个子查询，分别查找错误码、此前的认证问题，以及相关框架的信息。每个子查询聚焦一项需求，便于采用适合的匹配方式，避免整句话中的不同线索互相干扰。

3.  将每项需求交给合适的工具，必要时同时运行关键词检索和向量检索，再合并结果。精确字符串按原文匹配，问题描述按语义匹配。

4.  汇总取回的块。对于历史对话片段，按时间顺序放入上下文，并标明中间省略了哪些回合，让模型读到清楚的时间线。如果结果仍不足以回答问题，模型可以根据已经找到的线索调整查询，再次检索。

这些方法可以按处理复杂度分成几个层次，承载框架根据请求需要逐步使用。最基础的是近期窗口（recency window）：无论检索返回什么，都在上下文中保留最近几个回合，因为最新的往来通常与当前请求有关。在此基础上，关键词检索负责匹配精确字符串，向量检索负责匹配语义；简单请求可以只用一种，包含多种线索时则结合使用。再进一步，可以合并两个搜索器的排名，对靠前的结果重新评分。更复杂的情况，则让模型根据当前缺少的信息发起搜索，并在第一批结果不足时继续查找。

这四个例子说明了不同请求对检索的要求。实际使用时，承载框架需要根据需求组合方法，没有一种工具能包办所有请求。结果合并、重新评分，以及由模型主动发起搜索，留到后面的章节继续讨论。
